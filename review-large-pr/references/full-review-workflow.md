# Complete review workflow

Use this workflow for every invocation of `review-large-pr`, alongside the snapshot, requirements, validation, coverage and delivery rules in [SKILL.md](../SKILL.md). Keep the existing Astra/xhigh lead and verified evidence. Assess investigation depth from the change; delegation depends on independent work and capacity. Reuse sufficient architectural context.

## Prepare architectural context automatically

First inspect supplied or PR-linked designs and added/modified/renamed Markdown paths in the complete inventory at the recorded head for the top-level YAML key `document_feature_design`. If these yield no candidate, search that literal marker in established documentation locations at the same snapshot before reading documents broadly. The [discovery metadata contract](../../document-feature-design/references/discovery-metadata.md) defines the supported version, primary-document marker, and direct section pointers. A text match inside an example is not metadata. This is a cheap candidate search; do not scan every repository document before trying a relevant marked design.

For a supported marker, read the overview and follow its source-inventory, review-map, invariant, and scenario pointers. Check the relevant scope, source snapshots, current entry points, and a representative execution path against this PR. An older source baseline can still apply, including when the document was committed after the code it inspected; assess material differences instead of requiring its baseline to equal the containing commit. Select or combine relevant scopes when several designs exist. If the context is sufficient and applicable, record the document path and blob/revision plus the applicability evidence, then proceed to the whole-change model: skip broader context discovery, companion invocation, and repeated full design validation. It never skips the linked-requirements check, code, integration, or coverage review. Metadata is not proof of approval or correctness.

If no usable marker is found, its pointers are broken, its version is unsupported, or material context is missing or outdated, continue normal assessment of supplied designs, repository ADRs/specifications, and previous review context. Unmarked documents remain eligible for reuse; metadata failure alone does not require regeneration. Identify authoritative decisions and intended before/after behavior, contracts, critical invariants, review map, and integration scenarios. Follow a representative execution path at the recorded revisions to assess sufficiency. Record sources, snapshots, the assessment, and material gaps in the review record.

- **Sufficient and applicable:** reuse the existing documents and link their map, invariants, and scenarios. Add review-specific navigation in the record when needed. An older document revision or different headings alone do not make the context stale; assess relevant claims, entry points, contracts, and scenarios against the change. Do not generate a duplicate design just to fit a template.
- **Small descriptive gap:** add a concise provisional model to the record with its question, source trace, assumptions and limits; no companion invocation is required when this resolves the gap. Do not promote it to accepted intent.
- **Missing or materially incomplete:** automatically load and follow the [document-feature-design skill](../../document-feature-design/SKILL.md) to create a proportional, source-grounded local architecture draft. Include the missing review map, critical invariants, and integration scenarios, linking useful existing material instead of restating it.
- **Outdated descriptive context:** use that same skill to refresh an existing review-local draft or create a local supplement to a canonical document, preserving valid portions and identifying what changed. A conflict between code and an accepted requirement is a potential defect or unresolved decision, not permission to rewrite the requirement to match the code. Preserve authoritative rationale and record the divergence for investigation.

This context preparation is part of the single review invocation; do not require the user to invoke the companion separately. Sufficient context requires no documentation worker. For needed authoring, the existing lead applies the shared model policy and passes the documentation-author role, lead identity, companion skill path, review scope, exact source snapshots, existing authoritative links, gaps, validation plan and an explicit destination alongside the review record outside tracked source. Keep the result a review-local draft; do not amend accepted ADRs or tracked documentation without user authority. Separate documented intent, observed implementation, inference, and unknowns. Do not invent approval or historical rationale. The lead verifies the returned evidence, runs or checks the companion's semantic and structural validation, records the model decision and results or limitations, and continues the review without another user request.

Keep preparation bounded to the context needed to investigate this change. Missing rationale or inaccessible sources remain explicit gaps; they do not justify inventing context or stopping all useful code review. If the companion is unavailable, disclose that limitation and build a provisional model in the record. If the user explicitly forbids new documents, keep that model in the review record and respect the requested boundary.

## Establish the whole-change model

Use the reused or prepared context to orient the review, then independently verify its claims. Author summaries, generated drafts, maps, and passing tests do not establish completeness or correctness. Keep canonical definitions in the design and live review status, evidence, and findings in the review record. Creating context does not count as completing code review or automatically mark files reviewed.

Reuse applicable design units and their map, invariants and scenarios through the [handoff contract](../../document-feature-design/references/review-handoff.md). Add a review overlay of definition links, questions, evidence and dispositions; do not rebuild the design tables. Define new units only for uncovered behavior or material changes. Account for every changed path and relevant unchanged callers or dependencies; one file may participate in several units. Allocate deeper investigation to consequential state, ownership, authorization, compatibility, or external-effect boundaries. When useful, inspect logical commits for the development sequence, but evaluate the final combined diff. Keep substantial mechanical changes distinguishable from behavior changes without requiring history edits.

Assess investigation depth separately from file count. Use `deep` for substantial interacting new behavior, consequential cross-boundary uncertainty, explicit deep-review requests, or a prior pass whose evidence does not demonstrate sufficient investigation. Very large behavioral PRs require it; a large generated/mechanical diff alone does not. A compact consequential change within the review can also require deep investigation. Record `standard` or `deep` with actual behavioral evidence. For deep work, read [behavioral depth and independent challenges](behavioral-depth.md) and use its completion gate. Neither depth has a finding-count quota.

## Delegate selectively under one lead

The designated lead is the single review owner, whether it is the primary agent or the one assigned under the shared policy. After establishing the snapshot, complete inventory, and architectural context, automatically spawn focused subagents when bounded investigations can proceed independently and delegation would materially improve focus or elapsed time. This skill requests that delegation without a separate user instruction; respect available tools, session limits, and explicit user constraints. Start with two or three reviewers when useful, capped by remaining capacity after the coordinator/lead and any documentation worker; do not spawn agents to meet a quota or solely because the diff is large. Use sequential review for small follow-up deltas, tightly dependent reasoning, conflicting shared-resource needs, or unavailable/prohibited delegation. Record the delegation decision, requested model/effort, available execution evidence and brief rationale, then continue useful work.

Assign behavioral units or concrete questions from the map, with one primary reviewer per unit and deliberate overlap only where a consequential boundary warrants it. Give each reviewer its reviewer role/lead identity, the skill path, shared before/after overview, repository identities and exact base/comparison/head revisions, authoritative context links, relevant invariants and scenarios, assigned scope and dependencies, and a distinct evidence destination. Include the linked-requirements assessment and validation plan, including suite ownership and environment readiness; a fresh-context worker must receive this packet explicitly. Assign investigation questions without prescribing conclusions. Reviewers may follow callers and contracts beyond the starting file list and must flag newly discovered overlap or gaps to the lead.

Within a unit, assign bounded behavioral batches with a concrete question, required evidence and next checkpoint. Avoid giving one worker an entire new subsystem plus many unrelated responsibilities as a single undifferentiated pass. Reserve lead capacity for integration and judgment; delegate or sequence setup/CI accounting when it competes with that work. Rebalance only unfinished independent batches when capacity frees, retaining one owner and all completed evidence. More agents or shorter arbitrary file quotas are not the goal.

Delegated reviewers handle only their assigned investigation: they do not restart whole-PR context preparation or delegate further. Require a concise handoff containing unit IDs, the exact reviewed snapshot, actual paths/symbols/scenarios examined, proposed per-file dispositions, precise evidence locations and conclusions, candidate findings with trigger/consequence/source evidence, checks and results by category, assumptions, and remaining gaps. A single handoff may cover several files when it names their specific evidence; do not duplicate whole transcripts. A completion message or unsupported clean verdict is not coverage evidence.

Use the [behavioral investigation template](../assets/behavioral-investigation-template.md) for primary/challenge batches or an equivalent handoff. Save each completed batch before taking the next one; return unread/truncated regions and unresolved hypotheses explicitly. The lead reconciles these incremental handoffs into coverage rather than waiting for every worker's final response.

Keep the source review read-only. Give reviewers separate scratch outputs and isolated test execution where shared writes would conflict. The lead alone updates the consolidated review record and coverage inventory; reviewer notes are inputs to reconcile. While reviewers work, the lead investigates the primary flow and cross-unit scenarios, resolves dependencies, and checks unassigned areas. Wait for relevant handoffs before claiming completion; if a reviewer fails or returns partial work, the lead completes or reassigns the gap, or reports it explicitly as unfinished.

The lead owns integration, complete-inventory reconciliation, and the final findings. Check handoff revisions and inspect their evidence, independently verify candidate findings and resolve disagreements, then deduplicate by root cause and impact. Directly investigate consequential interactions even when every unit reports no findings. Do not replace this work with a vote or repeat all unit reviews merely to obtain agreement. Carry forward results from a different snapshot only through the [revision-reassessment process](../SKILL.md#resume-after-changes-and-deliver-a-verdict).

## Review units and their interactions

Work in bounded passes, loading relevant source and dependencies as needed. A unit's file list is a starting point, not a boundary that forbids following a call or contract. Record findings, evidence, unresolved questions, and the next step before switching context. Opening a file or receiving an agent summary does not establish that it was reviewed.

Perform an explicit integration pass across the changed units and relevant unchanged consumers. Trace the material scenarios from the actual design: ordinary behavior, failure or interruption boundaries, recovery, and compatibility or rollback where affected. Link the scenario definition and record the tested variant or material delta, violated or preserved invariants, and independent evidence. Describe starting state, order, expected effects and responsible components only where absent or changed in the linked definition. For stateful, cached or gated flows, select relevant cold-start versus warm-state, restart, configuration-change and dependency-recovery scenarios. Check both safe rejection and eventual progress: which component refreshes unavailable state, what wakes retries, and whether recovery depends on unrelated traffic. Trace new dependencies through admission, execution and recovery, including retained work; avoid imposing these scenarios on changes where they do not apply. Choose scenarios for this change instead of mechanically applying a catalog. A passing component test does not prove the behavior of a cross-component sequence.
